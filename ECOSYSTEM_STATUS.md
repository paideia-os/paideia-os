**Snapshot:** 2026-09-06 (third refresh — XRW-01..06 cascade + paideia-as v0.33.1 + R106 kickoff).

## Recent session activity (since the 2026-09-02 snapshot)

- **XRW-01 through XRW-06 cross-repo waves landed.** Six submodule-bump sweeps closed roughly 30 issues across `paideia-as` and its satellites: XRW-01 (5 satellites, 5 issues), XRW-02 (4 satellites, 5 issues), XRW-03 (`paideia-as` close-out), XRW-04 (2 satellites, 10 issues), XRW-05 (2 satellites, 6 issues), XRW-06 (`paideia-as`, 2 issues). The three volume tools picked up the R90-XREPO.013.M4-001 line-grammar `caps.decl` format in this cascade, each closing its own `caps.decl` issue.
- **`paideia-as` jumped v0.29.2 → v0.33.1** (five point releases in-session): a `no_std`/`alloc` crypto-FFI refactor into per-primitive files, then **ML-KEM-768 (FIPS 203)** landed as a full KEM alongside the existing MLDSA65 (FIPS 204) signature suite, plus a KAT-vector hw-smoke test pass and retrospective release notes for v0.25–v0.33. Open count moved 2 → 3 (`#1348` shim umbrella closed; `#1396` debt-catalog umbrella and `#1392` BLAKE3 intrinsic request opened; `#1346` ECDSA-P256 carries over).
- **`libpdx-elevate` v1.1.1 → v1.1.2**: LE.M5 attestation-delegation record + required-flag gate, and LE.M7 revoke-cascade-over-child-chain both landed. 18 → 12 open. LE.M2's real-audit-swap is still the one **load-bearing cross-repo block**: `libpdx-elevate#38` needs a `!{mem}`-only `audit_append_leaf` primitive from `libpdx-audit#31` (the trio it has today carries `!{mem, sysreg}` effects that would force a v2.0 cap-manifest ripple through every downstream tool). LE.M6 (`#33`/`#34`, signed audit sink) is blocked transitively on the same primitive.
- **`ls` v1.0.0 → v1.1.1**: a real feature wave landed — multi-column TTY output, `-t`/`-S`/`-r` sort flags, `-R` recursion (interim), file-as-path single-row emit, `--group-directories-first`, plus a JSON-escape correctness fix. 20 → 7 open.
- **Volume-tool trio caps.decl + elevate landings.** `mount.pdxfs` (1 → 0 open) and `umount.pdxfs` (3 → 0 open) both closed their `caps.decl` issues via the XRW cascade; `umount.pdxfs` additionally landed its `LE-001` elevate gate on `/system` unmount. `mkfs.pdxfs` (2 → 1 open) closed its `caps.decl` issue and fully **specified** (design-only, no wiring) its own `LE-001` elevate gate on block-device format — still blocked on an honest `parent_ep_slot`/`reply_ep_id` value and on `paideia-os/tools/build.sh`'s R64v2 link line, which deliberately excludes `libpdx-elevate` from this tool today.

- **R106 (persistent /home + content-addressed identity) kicked off.** `R106.M1-001` seeds `/home` + placeholder-fingerprint home dirs in `rootfs_seed`; `R106.M3` retired the `/home/operator` hardcode (`#2230`); `R106.M6` closed the persistent-`/home`-substrate round. Both are R106-wave work-in-progress, not regressions; neither is a library-ABI-forced kernel change, so every Table 3 "Kernel-side hits" cell below still reads 0.

## Legend

**Semaphore convention.** Each repo is scored on a 5-segment maturity bar `[█████]` → `[█░░░░]`, then bucketed into a red/yellow/green semaphore for at-a-glance triage:

| Bar | Segments | Status | Meaning |
|---|:-:|:-:|---|
| `[█████]` | 5 | 🟢 | Signed release + M5 closed + downstream consumers active. |
| `[████░]` | 4 | 🟡 | Tests landed + M4 closed. |
| `[███░░]` | 3 | 🟡 | Real body implemented + M2/M3 closed. |
| `[██░░░]` | 2 | 🔴 | Scaffold in + M1 closed. |
| `[█░░░░]` | 1 | 🔴 | Repo exists only (auto-README, no code body). |

Sort within each table: **Status ASC** (🔴 first), then **Dependent repos DESC** — the goal is to make the highest-blast-radius under-built repos read first.

**OS changes needed** is the count of *open* issues in the `paideia-os/paideia-os` monorepo that this satellite requires before it can finish its own open milestones. The monorepo now carries **2 open issues** (`#2345`, `#2341`, both R106-wave) but neither forces an ABI-visible kernel change any satellite is gated on, so every column below still reads 0.

**Dependent repos** is the count of other satellites in the org whose issues, plans, or design docs reference this repo as a build-time or run-time dependency. Where the count is small (≤5), the dependents are listed inline; otherwise only the count is shown to keep the table readable.

Library maturity scores are inherited from `design/library-status.md` (this repo's canonical library tracker, which is refreshed by a different pass and stays independently maintained), with one exception this snapshot (`shell`, corrected here — see above). Tool maturity scores are computed here from a fresh audit — commit count, release tags, per-milestone `open:closed` ratio, presence of `caps.decl`, and whether any downstream design doc treats the tool as landed, weighed against actual code-body evidence rather than tag/milestone bookkeeping alone.

### Reading the matrix

- **Row scope.** A row's downstream cells list every satellite that would need at least a re-verify pass on a minor-behavior release of the updated repo. A *breaking* release additionally forces every downstream to bump its submodule pin and re-run its own M4 smoke.
- **Kernel-side hits.** A library update forces a monorepo change when the library's ABI touches a kernel-owned surface — a `KIND_*` dispatch table, a syscall number, a daemon name, an audit record shape. The monorepo carries **2 open issues** this snapshot (`#2345`, `#2341`), up from 0 — both are R106-wave (persistent-home / content-addressed-identity / shell-satellite) work-in-progress, neither triggered by a library ABI change, so every row still scores 0.
- **Transitive.** These are direct dependencies only. `libpdx-cap` transitively touches every kernel surface via the downstream tools, but the matrix records only the surfaces `libpdx-cap` itself binds against.
- **New this snapshot:** `libpdx-elevate`'s retirement of `elevate_client_request` in favor of `acquire`/`_require`/`cap_derive`/`revoke_cascade` opened migration tickets on `rm` (`#29`,`#30`), `mv` (`#29`), and `pkg` (`#40`) — the first cross-repo churn wave driven by `libpdx-elevate`'s own API evolution rather than a kernel or `paideia-as` change.
