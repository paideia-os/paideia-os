# R16-M3 KPTI sweep — #733 #734 #738 #739

## 1. Scope

Close the four remaining known KPTI-class defects that were siblings of the
already-fixed #724 D4 / #730 D10c / #730 D10d / #737. All four have the same
root cause: a kernel path reads or writes a user VA under kernel CR3 (=
`_kernel_pml4_pa`, the boot PML4 installed by `syscall_entry`'s CR3 flip),
which hits whatever kernel byte the boot PML4's low identity map covers
PA=`user_va` with — NOT the per-process user PML4's frame for that VA.

| Issue  | Site                         | Direction       | Reachability at HEAD             |
|--------|------------------------------|-----------------|----------------------------------|
| #733   | `sys_open` path-string read  | user → kernel   | Firing today (init /dev/tty0)    |
| #734   | `sys_write` fd>=3 buf read   | user → kernel   | Latent (no fd>=3 write callers)  |
| #738   | `tmpfs_read` rep_movsb dst   | kernel → user   | Latent (no user `read()` yet)    |
| #739   | `tty_read_try` byte-store    | kernel → user   | Latent (no user `read(tty)` yet) |

## 2. Wire evidence — pre-fix

`boot_r17_init` fingerprint at commit `cf23e2c` (pre-sweep baseline) passes
because #723's on-wire acceptance chain (`CHILD HELLO 42\nWAIT: pid=2
status=42\nREAPED\n`) uses only the UART fast path (`dispatch_write_uart`
for fd 1/2 and `sys_debug_puts` via `dispatch_debug_puts`), both already
walk-safe from #724 D4 and #730 D10c. Init's stdio setup — the actual
`sys_open("/dev/tty0")` call — silently fails with `-ENOENT` and init
doesn't check the return, so `dup2(3, 0)`/`dup2(3, 1)`/`dup2(3, 2)` fail
silently too. This masking is why the four sibling latents survived through
the R17.M0 close.

Independent evidence of the failure was captured by the debugger during
#730 D10 verify at commit `29071dc`: `sys_open_body → vfs_open →
path_resolve` reads `[user_path_va]` under kernel CR3 and sees a NUL at
byte 0 (init's path lives at user VA ~0x400000+, PA `0x400000+` sits inside
kernel `.bss` which is zero-initialised by boot). `path_resolve` returns
`vnode_idx=0`, `vfs_open` returns 0, `sys_open_body` returns `-ENOENT`.

The other three sites are structurally identical, but their downstream
callers don't exist yet — a `read()` from any userland program would land
its file bytes into a random kernel physical page; the user would observe
zeros where their file's contents should be.

## 3. Root cause

Under strict-KPTI (post-#502 `syscall_entry` semantics), the trampoline
flips `cr3` to `_kernel_pml4_pa` (the boot PML4) before dispatching to
`syscall_dispatch`. The boot PML4:

- `PML4[0..255]`  — 1 GiB huge PDPT covering PA `0..4 GiB` as low identity
- `PML4[256]`     — kernel higher-half identity map (also 1 GiB huge PDPT)
- `PML4[261]`     — trampoline data at fixed VA (survives CR3 flip)

The per-process user PML4 (installed by `aspace_map` from the ELF loader
and `sys_execve_body`) shares `PML4[256..]` with the boot PML4 but installs
`PML4[0..255]` with per-process 4 KiB leaf mappings (VA→frame for the
process's text, data, BSS, stack). Those leaves are NOT reflected into the
boot PML4.

So a raw `mov_b rax, [user_va]` or `mov [user_va], eax` executed under
kernel CR3 sees only the boot PML4's low identity mapping. For any user VA
< 4 GiB, the access silently redirects to PA = VA — which lands somewhere
in kernel data (.bss, .rodata, or unused low-memory), never the user
program's real frame.

The same-issue landing pattern that closed #724 D4, #730 D10c, #730 D10d,
and #737 established a helper convention: for each user VA touch, walk
`_current_tcb.user_pml4_va → PDPT → PD → PT → frame`, then complete the
access via the kernel higher-half identity map at `frame_pa +
KERNEL_VMA_BASE`. This landing extends the helper family with fixed-length
byte copies (previously only fixed-width u32 or NUL-terminated string) and
routes the four remaining known sites through them.

## 4. Site enumeration

### 4.1 #733 — `sys_open` path-string read

`dispatch_open` (pre-fix):

```asm
dispatch_open:
mov rax, [rip + _current_tcb];
mov rdi, rax;                         // rdi = current
// rsi=path, rdx=flags, rcx=mode already positioned by SysV
sub rsp, 8;
call sys_open_body;                   // reads path bytes downstream
add rsp, 8;
ret;
```

`sys_open_body` forwards `rsi` (user path VA) to `vfs_open`, which calls
`path_resolve(rdi=path_ptr, ...)`. `path_resolve` byte-scans the path via
`mov_b rax, [r12]` at `src/kernel/core/fs/path.pdx:74`, and `vfs_open`'s
O_CREAT branch does its own scan at line 121 with `mov_b rax, [rbx +
r8*1]`. Both fire under kernel CR3 on `rsi`/`rbx` = user VA.

### 4.2 #734 — `sys_write` fd>=3 buf read

`dispatch_write` (pre-fix, fd>=3 branch after `user_ptr_ok`):

```asm
mov rax, [rip + _current_tcb];
mov rdi, rax;
// rsi=fd, rdx=buf, rcx=len already positioned by SysV
sub rsp, 8;
call sys_write_body;                  // forwards rdx (user buf VA) down
add rsp, 8;
ret;
```

`sys_write_body → vfs_write → vops_write → tmpfs_write` (or `tty_write`).
`tmpfs_write`'s `rep_movsb` (`src/kernel/core/fs/tmpfs/write.pdx:114-119`)
does `mov rsi, rbx` where `rbx = buf_ptr = user VA`, then `rep_movsb`
copies bytes from the wrong physical page into the tmpfs backing frame.
`tty_write`'s byte-loop (`src/kernel/core/tty/write.pdx:60-62`) has the
same shape.

### 4.3 #738 — `tmpfs_read` rep_movsb dst

`tmpfs_read` at `src/kernel/core/fs/tmpfs/read.pdx:114-120`:

```asm
mov  rsi, r8;                        // src = page_va + intra (kernel VA — safe)
mov  rdi, rbx;                       // dst = buf_ptr  ← USER VA under KERNEL CR3
mov  rcx, r14;                       // count = n
cld;
rep_movsb;
```

`rbx = buf_ptr` from `sys_read_body`'s call chain (originally from
`dispatch_read` which passes the user VA straight through). `rep_movsb`
writes to the boot PML4's identity-mapped PA for that VA, not the user
program's frame.

### 4.4 #739 — `tty_read_try` byte-store

`tty_read_try` at `src/kernel/core/tty/read.pdx:79-83`:

```asm
// dst byte
mov  r9, rsi;                        // rsi = buf = user VA
add  r9, rcx;
mov_b [r9 + 0], rax;                 // ← USER VA under KERNEL CR3
```

Reachable via `sys_read → vfs_read → vops_read → tty_read → tty_read_try`
for any future stdin `read()`.

## 5. New helpers

Both are leaf helpers (no nested call) in
`src/kernel/core/syscall/user_read.pdx`, joining the existing
`user_puts_via_walk` (#724 D4), `user_read_str_via_walk` (#730 D10d), and
`user_write_u32_via_walk` (#737).

### 5.1 `user_read_bytes_via_walk(kernel_dst, user_va, len) -> u64`

Read exactly `len` bytes from `user_va` into `kernel_dst`. Structural
mirror of `user_read_str_via_walk` minus the NUL early-exit — the loop
runs the full `len` iterations. Per-byte 4-level walk of
`_current_tcb.user_pml4_va` → PDPT → PD → PT → frame, then read via the
kernel higher-half identity map and store to `kernel_dst[i]`.

- Return `rax = 0` on success (all `len` bytes copied).
- Return `rax = 0xFFFFFFFFFFFFFFF2` (-EFAULT) on:
  - NULL `_current_tcb` or NULL `user_pml4_va`;
  - unmapped page at any of the 4 levels;
  - PS=1 huge page at PDPT (1 GiB) or PD (2 MiB) — `aspace_map` only
    installs 4 KiB leaves for user pages, but the check is defensive.

Partial `kernel_dst` content on failure is UNDEFINED — the caller must
either treat the copy as atomic-success or discard the buffer.

### 5.2 `user_write_bytes_via_walk(user_va, kernel_src, len) -> u64`

Symmetric write counterpart. Walk `user_va`, then store bytes read from
`kernel_src[i]` (direct kernel-VA load, no walk needed on the source side)
to the leaf kernel VA. Return convention identical to
`user_read_bytes_via_walk`.

### 5.3 Why leaf helpers with a 5-push prologue

Neither helper does a nested call, so a callee-save prologue is
technically unnecessary for SysV alignment. We use the 5-push (rbx, r12,
r13, r14, r15) shape purely for uniformity with `user_read_str_via_walk` —
future extensions may add nested calls (e.g., a per-page mode that
inline-checks for PS=1 recovery) without needing to re-derive the register
plan.

## 6. Fix approach — Option B (dispatch-layer once)

The plan initially framed Option A (fix at each buggy site: modify
`sys_open_body`, `sys_write_body`, `tmpfs_read`, `tty_read_try` to accept
user VAs and internally walk). **This is not viable** because the same
functions are exercised by `kernel_main`'s bring-up witnesses with
KERNEL-VA pointers:

- `sys_open_witness` (kernel_main.pdx:4054+) passes `[rip +
  witness_path_slash]` — a kernel VA.
- `sys_read_witness` (:4278) and `sys_write_witness` (:4400) pass
  `[rip + tmpfs_*_buf]` — kernel VAs.
- `tty_vops_witness` (:5589) passes `[rsp + 0]` — a kernel stack VA.

Any body-level walker would fail the walk on those kernel-half VAs
(PML4[256+] is huge-PS PDPT — the walker rejects on the first `PS=1`
check), regressing five witness suites simultaneously.

**Option B** (fix at dispatch layer) keeps the body/backend contracts
unchanged — they continue to say "buf is kernel VA" — and adds a single
user↔kernel bounce at the syscall dispatch boundary, exactly the layer
where the CR3 mismatch first becomes observable. The witnesses continue to
operate directly against `sys_*_body` and `tmpfs_read` / `tty_read` /
`tty_read_try` without ever entering the dispatch layer.

The design precedent is #737, which fixed `dispatch_wait4_writeback` at
the dispatch layer (not `sys_wait_body`) using the same walker family.

## 7. Site fixes (Option B)

### 7.1 Scratches

Three `.bss` slabs declared at module scope in `dispatch.pdx`:

- `_dispatch_open_path_scratch  : [u8; 256]  = uninit @align(8)` — matches
  `DISPATCH_PATH_MAX` (aligned with `_vfs_open_parent_scratch` and
  `_execve_path_scratch`, which both use 256).
- `_dispatch_read_buf_scratch   : [u8; 4096] = uninit @align(8)` — matches
  `DISPATCH_IO_MAX`, aligned with tmpfs single-page ceiling
  (`tmpfs/read.pdx §4.7` and `tmpfs/write.pdx §4.5`).
- `_dispatch_write_buf_scratch  : [u8; 4096] = uninit @align(8)`.

### 7.2 `dispatch_open` (#733)

Before invoking `sys_open_body`, walk-copy the user path into
`_dispatch_open_path_scratch` via `user_read_str_via_walk`. Pass the
scratch VA (kernel) as `rsi` to `sys_open_body`. On walker failure (NUL
before terminator, unmapped page, kernel-half VA) return `-EFAULT`.

Alignment: entry `rsp%16==8`. Two argument-preserve pushes (rdx=flags,
rcx=mode) plus a `sub rsp, 8` alignment pad reach `rsp%16==0` for the
walk call; symmetric `add rsp, 8` + two pops restore before
`sys_open_body`'s own `sub rsp, 8` pad.

### 7.3 `dispatch_write` fd>=3 branch (#734)

After `user_ptr_ok`'s range check succeeds and fd is not in {1, 2} (UART
fast-path already walk-safe from #730 D10c), cap `len` at
`DISPATCH_IO_MAX = 4096`, walk-copy `[user_va, user_va+len)` into
`_dispatch_write_buf_scratch` via `user_read_bytes_via_walk`, then pass
the scratch VA as `rdx` (buf) to `sys_write_body`. On walker failure
return `-EFAULT`.

The length cap gives POSIX-legal short writes; `sys_write_body`'s own
`fd_table` offset advance uses the returned `bytes_written`, so the
fd-position is correct regardless of the cap.

### 7.4 `dispatch_read` (#738 + #739)

Cap `len` at 4096, save the original user buf VA (in `r15`) and capped
len (in `r14`) across `sys_read_body`, pass `_dispatch_read_buf_scratch`
as `rdx` (buf). After `sys_read_body` returns:

- `rax == 0` (EOF): fast-path skip the walk copy.
- `rax > cap` (errno sentinel like `-EBADF`, `-EIO`): pass through
  without touching user buf.
- `rax` in `[1, cap]` (bytes read): walk-copy
  `_dispatch_read_buf_scratch[0..rax]` back to the user buf via
  `user_write_bytes_via_walk`. On walker failure return `-EFAULT`;
  otherwise return the original `bytes_read` value.

This single fix covers BOTH #738 (tmpfs backend) and #739 (tty backend)
because BOTH `tmpfs_read` and `tty_read_try` now receive the kernel
scratch as their `buf_ptr` — their internal `rep_movsb` / byte-store
loops land bytes into safe kernel memory. The user copy is deferred to
after `sys_read_body` returns, at the dispatch layer.

### 7.5 What did NOT change

- `sys_open_body`, `sys_read_body`, `sys_write_body`: contracts and code
  unchanged. Witnesses continue to pass kernel VAs; production path now
  gets a kernel scratch from dispatch.
- `vfs_open`, `vfs_read`, `vfs_write`, `vfs_close`: no change — their
  documented contracts already say "kernel VA" and are honoured by the
  witnesses and by the post-fix dispatch path.
- `path_resolve`, `tmpfs_read`, `tmpfs_write`, `tty_read`,
  `tty_read_try`, `tty_write`: no change — same reason.
- `sys_execve_shim`: no change — already fixed at #730 D10d.
- `dispatch_wait4_writeback`: no change — already fixed at #737.
- `dispatch_debug_puts` and `dispatch_write_uart`: no change — already
  fixed at #724 D4 and #730 D10c respectively.

## 8. Concurrency assumption (R17.M0 only)

At R17.M0 the only user tasks are `init` (pid=1) and `child_hello`
(pid=2). Neither calls `sys_read`, and only `init` calls `sys_open` (once,
for `/dev/tty0`). No two tasks concurrently touch any dispatch scratch,
so the static (rather than per-task) allocation is race-free for this
landing. The write scratch is unreachable today (no fd>=3 write callers);
the read scratch is unreachable today (no fd>=3 read callers).

Once the shell (post-R17.M4) grows real stdin reads on `tty0`, two
possible races appear:

1. Task A calls `sys_read` on tty; `tty_read` blocks in `sched_block`;
   Task B runs, calls `sys_read` too, writes to the same scratch, and
   copies out. Task A wakes; its `tty_read_try` write overwrites Task B's
   already-consumed scratch — harmless (Task B is done). But Task A's
   walk copy at dispatch layer sees the correct bytes because it runs
   directly after `sys_read_body` returns, no yielding between.
2. Timer preempts Task A between `sys_read_body` return and the dispatch
   walk copy; Task B runs and enters `sys_read`, writing to the same
   scratch. Task A resumes and its walk copy now reads Task B's data.
   **This is a real race that would surface as corrupted user reads.**

Follow-up: move scratches into the TCB slab (add a `syscall_scratch :
[u8; 4096]` field), or allocate on the kernel stack (16 KiB per task, 4
KiB is affordable). Both approaches eliminate the race — track under a
new issue when shell stdin reads become common.

## 12. Follow-ups

- **Per-task scratch buffers**: required before concurrent sys_read on
  tty stdin becomes common (see §8). File a new issue when the shell
  grows real stdin reads.
- **Larger IO sizes**: the 4096 cap is the tmpfs single-page limit. When
  tmpfs grows multi-page support (or a real backing filesystem lands),
  the cap should be raised or the copy should loop chunk-by-chunk.
- **Ring-3 witness for #734/#738/#739**: currently no user program
  exercises these paths. Add a witness that opens a tmpfs file, reads
  it, and writes it to a different tmpfs file (exercises #734 + #738),
  plus a tty stdin echo test (exercises #739 pending #666 UART RX
  driver). Deferred as follow-up per plan.
- **Extend `user_ptr_ok` to Phase-2 per-page walk**: with helpers landed
  the range check can gate BEFORE the walk copy runs, eliminating
  wasted work on obviously-invalid pointers.
- **Consolidate KERNEL_VMA_BASE constant**: currently duplicated across
  `aspace_map.pdx`, `kpti.pdx`, `ptr_check.pdx`, and the four helpers in
  `user_read.pdx`. Not urgent — the movabs pattern makes the value
  self-documenting — but a single `pub let` would reduce audit noise.
